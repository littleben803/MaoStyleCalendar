# 跨年份内容池与日期分配规则

更新日期：2026-10-29

## 1. 产品结论

应用不属于 2027 年专版。它读取用户当前日历与时区，在每个自然年生成该年的完整日历；365 套插画与语录作为可重复跨年使用、但年内不重复的内容池。

插画与设计师指定的对应语录构成不可拆分的 `DailyContentPack`。分配时移动整套内容，不独立随机插画和语录。

## 2. 年度分配算法

建议采用版本化的确定性洗牌：

1. 基础池包含稳定排序的 365 个 `DailyContentPack.id`；
2. 种子由 `calendarYear + allocationAlgorithmVersion` 生成；
3. 使用固定、可测试的伪随机算法执行 Fisher–Yates 洗牌；
4. 普通年按当年第 1～365 天依次映射到洗牌结果；
5. 同一年同一版本在 App、Widget、iPhone、iPad、Mac 与重装后结果一致；
6. 新年使用新种子重新洗牌，基础池恢复完整可用状态。

这比“用户每打开一天就随机抽取并删除”更可靠，后者会受启动顺序、设备迁移和数据丢失影响。

## 3. 闰年

公历普通年为 365 天，闰年为 366 天。365 套内容无法同时满足“闰年每天都有内容”和“同一年绝不重复”。

推荐方案：

- 基础池保持 365 套；
- 额外制作 1 套 `LeapDayContentPack`，只用于 2 月 29 日；
- 闰年其余 365 天继续完整使用基础池；
- 非闰年不展示闰日专属内容。

在闰日专属内容交付前，该能力状态为产品阻塞项，不能通过偷偷重复一套内容解决。

## 4. 日期与版本稳定性

- 年度内容分配固定使用公历日期与用户当前 Time Zone；农历只用于展示，不以用户首选历法改变年度资源映射；
- 午夜更新受 WidgetKit 调度影响，不承诺 00:00:00 精确刷新；
- `allocationAlgorithmVersion` 发布后保持稳定；
- 修正文案、翻译或图片时保留原内容 ID；
- 如果未来必须移除某套内容，建立新的年度映射版本，并从下一自然年生效；
- 不在年中因 App 更新重新洗牌，避免用户当天内容和壁纸引用发生漂移。

## 5. 浏览范围

- 今日页跟随系统当前日期；
- 年度册默认打开系统当前年份，并展示该年所有日期；
- 进入新年后自动切换为新年度映射；
- 是否允许用户主动切换历史年份，留到 SwiftUI 实现前的业务边界确认；用户已取消前端交互原型。
